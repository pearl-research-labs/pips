## Abstract

This PIP specifies a version-2 Pearl Proof-of-Useful-Work (PoUW) certificate for grouped general matrix multiplication (Grouped-GEMM) workloads, with Mixture-of-Experts (MoE) inference and training serving as the primary motivating case.

In the version-1 Pearl PoUW protocol, a miner commits to two matrices, derives low-rank noise from the commitments and chain state, executes a noised tiled matrix multiplication, opens a winning tile, and supplies a succinct zero-knowledge proof that the opened computation is consistent with the commitments and satisfies the proof-of-work target. This works well when the useful computation is naturally represented as one large matrix multiplication. In MoE layers, the input activation matrix is naturally viewed row-wise, with each row corresponding to a token. A router assigns each token to several experts, so the useful work becomes a grouped collection of smaller expert matrix multiplications, rather than one dense multiplication. Treating each expert multiplication as an independent version-1 PoUW instance repeats commitment hashing, noise generation, and peeling work over the same activation data.

This PIP introduces a V2 certificate format that allows an MoE miner to achieve lower mining overhead. The miner commits once to a global activation matrix, once to the stacked expert-weight matrix, and once to the routing table. The miner then performs a Pearl-style noised Grouped-GEMM over expert-local activation batches and contiguous expert-weight slices. The verifier checks the usual Pearl PoUW tile-opening relation, with the additional requirement that the opened expert-local rows are consistent with the committed routing table and the committed global activation matrix. A dense MatMul is a special case of Grouped-GEMM, and can therefore be proven using a V2 certificate with virtually the same overhead. However, the V1 and V2 certificate details differ, so a winning dense-MatMul witness under V1 is generally not a winning Grouped-GEMM witness under V2.

## Motivation

Pearl's base PoUW protocol is designed around matrix multiplication: the useful computation is a product `A * B`, while the mining work is extracted from the execution trace of a noised tiled multiplication of committed inputs. The protocol adds low-rank noise to make each tile computationally hard and fair, collects intermediate states to obtain lottery tickets, and peels the noise to recover the useful product. The costs of commitment hashing, noising, tile hashing, and peeling are amortized by the size of the underlying GEMM.

MoE workloads break this amortization pattern. A batch of `M` tokens is routed to experts, and each expert receives only the subset of tokens assigned to it. If there are `n_E` experts and each token is routed to `k_top` experts, then the average number of tokens per expert is `M * k_top / n_E`.

A naive adaptation of Pearl PoUW would run the V1 protocol separately for each expert-local multiplication `A_e * W_e`, where `A_e` is the matrix of activations routed to expert `e`, and `W_e` is the expert's weight matrix. Because each expert-local multiplication has a smaller effective row dimension than the full dense batch, overheads that are negligible for a large GEMM can become visible.

This PIP preserves the security and lottery semantics of Pearl PoUW while matching the execution pattern of MoE workloads: grouped matrix multiplications.

## Algorithmic Overview

Running the V1 protocol independently for each expert-local multiplication repeats work that is naturally shared in an MoE grouped-GEMM workload:

1. **Repeated activation commitment.** The same token activation may be routed to several experts. In the naive construction, that activation is hashed repeatedly as part of multiple expert-local matrices.
2. **Repeated activation noising.** Each expert-local `A_e` is noised as a separate input matrix, even though its rows are gathered from a single global activation matrix.
3. **Repeated peeling against shared activations.** Peeling terms involving the activation matrix are recomputed for the same activation rows across multiple expert-weight matrices.

The V2 protocol keeps the version-1 Pearl PoUW structure, but changes the order in which noising, routing, and peeling are applied. The key change is that V2 treats the MoE computation as one routed grouped-GEMM instance, rather than as many independent GEMM instances.

At preprocess time, once per relevant blockchain update, the miner commits to the expert weights as one horizontally stacked matrix

```
W = [W_0 || W_1 || ... || W_{n_E-1}]
```

and derives the weight-side noise factors `E_BL` and `E_BR`. Since each expert weight matrix `W_e` is a contiguous slice of `W`, the same left noise factor `E_BL` is shared across all experts.

The miner then commits once to the global activation matrix `T`. This single commitment is used to derive the activation-side noising before routing. Logically, it first forms the noised global activation matrix and only then gathers expert-local batches from the already-noised rows:

```
T'   := T + E_AL E_AR
A'_e := GatherRows(T', route[e])
```

This means that if the same token is used by several experts, its activation row is noised once and reused across the corresponding expert-local products.

Finally, we need to peel the noised result. In V1 the denoising terms are:

```
A' B' - AB = (A E_BL) E_BR + E_AL (E_AR B')
A' := A + E_AL E_AR,
B' := B + E_BL E_BR.
```

In V2 since `E_BL` is common to all expert slices, the first peeling term

```
T * E_BL
```

is evaluated once over the global activation matrix. The result is then routed to the relevant experts, instead of recomputing the same activation-by-noise product separately for each expert-local multiplication.

After these shared steps, the miner executes the noised grouped GEMM over the routed expert batches and contiguous expert-weight slices. A winning tile is still an opened noised matrix-multiplication trace, as in V1.
The opened rows and columns in the expert-local multiplication `A_e * W_e` are authenticated through a Merkle proof of `T`'s rows and `W`'s columns.

## Specification

### Certificate Version

This PIP assigns Pearl PoUW certificate version `0x02` to Grouped-GEMM proofs.

```
certificate := version || bytes
version     := 0x02
```

Version-2 certificates are not valid under version-1 validation rules. Activation is therefore a consensus hard fork: upgraded nodes MUST parse and verify version-2 certificates according to this specification, while non-upgraded nodes will reject blocks using this certificate version.

This PIP does not change the block identity rule. As in the existing certificate mechanism, certificate bytes are not part of the block identifier. The block header contains `pouw_meta`, a commitment to the public PoUW witness data, and the certificate proves that the committed witness satisfies the version-2 relation.

### Notation

Let:

```
T      := global activation matrix, token-major, shape M x d
W      := stacked expert-weight matrix, shape d x (n_E * h)
n_E    := number of experts
k_top  := number of experts selected per token
R      := low-rank noise parameter
sigma  := chain state used for PoUW seed derivation
mu     := mining configuration
```

For expert `e`, let:

```
route[e] := ordered list of u32 token indices routed to expert e
A_e      := GatherRows(T, route[e])
W_e      := contiguous expert slice of W belonging to expert e
C_e      := A_e * W_e
```

The useful computation certified by this PIP is:

```
for each expert e:
    C_e = A_e * W_e
```

All `W_e` are contiguous slices of one committed matrix `W`. All `A_e` are gathered from one committed activation matrix `T` according to the committed routing table.

### Commitments and Routing

A version-2 PoUW instance has three primary commitments:

```
H_T := CommitmentHash_T(T, mu, sigma)
H_W := CommitmentHash_W(W, mu, sigma)
H_R := CommitmentHash_R(route, mu, sigma)
```

`H_T` commits to the global activation matrix in token-major order.

`H_W` commits to the stacked expert-weight matrix. Expert `e` occupies a deterministic contiguous slice of `W`; the slice layout is part of `mu`.

`H_R` commits to the routing table. The routing table is expert-major: for each expert `e`, it contains the ordered list of global token indices assigned to that expert.

```
route[e] = [token_index_0, token_index_1, ...]
```

Each `token_index` is encoded as a `u32`. The `j`-th row of the expert-local matrix `A_e` is:

```
A_e[j, :] = T[route[e][j], :]
```

The consensus serialization need not literally encode a map. The intended layout is expert-major concatenation: token-index lists are concatenated in expert order, with routing offsets or lengths identifying the segment belonging to each expert. Any equivalent serialization MUST bind:

- the expert identifier;
- the number of tokens assigned to the expert;
- the ordered `u32` token-index list for that expert;
- sufficient offsets or lengths to authenticate opened routing elements unambiguously.

A verifier MUST check that opened routing elements used by a winning tile are authenticated by `H_R`. For the exposed routing elements in the opened tile, the verifier MUST also check that the exposed token indices are monotonic in tile order.

The verifier does not recompute routing from router weights or logits. The routing table is treated as committed input to the grouped-GEMM PoUW instance.

### Seed Derivation

The activation-side hash used for seed derivation is modified in grouped mode. Let `routing_offsets` denote the canonical expert-major offsets or lengths needed to parse the routing layout. Define:

```
routing_offsets_bytes := LE64(routing_offsets[0]) || LE64(routing_offsets[1]) || ...
H_T_grouped           := BLAKE3(H_T || H_R || routing_offsets_bytes)
```

The two low-rank-noise seeds are:

```
s_W := BLAKE3(job_key || H_W)
s_T := BLAKE3(s_W || H_T_grouped)
```

where `job_key` is the chain-state and mining-configuration key used by the PoUW instance.

For non-grouped mode, `H_T_grouped` is replaced by the ordinary left-matrix commitment hash. In grouped mode, including `H_R` and `routing_offsets_bytes` binds activation-side noising to both the global activation matrix and the expert-major routing layout.

The exact byte encodings of `job_key`, `H_T`, `H_W`, `H_R`, and `routing_offsets_bytes` are deferred to the reference implementation. They MUST be canonical and collision-resistant.

### Mining Configuration

The version-2 mining configuration `mu` contains all fields required by the version-1 matrix-multiplication verifier, plus the grouped-GEMM fields needed to interpret `T`, `W`, and `route`:

```
mu := {
    mode: GROUPED_GEMM,
    matmul_accumulate_type,
    activation_shape: (M, d),
    expert_weight_shape: (d, h),
    expert_count: n_E,
    route_commitment_shape,
    noise_rank: R,
    tile_shape: (t_m, t_n),
    depth_tile_shape,
    difficulty_bits: b,
    weight_slice_layout,
    commitment_layout_ids,
    snark_statement_id
}
```

Concrete bounds for `M`, `d`, `h`, `n_E`, `k_top`, route size, and supported tile families are deferred to the activation parameters and reference implementation.

### Noise Generation

Version 2 uses the version-1 low-rank-noise paradigm, applied to grouped inputs.

For each expert `e`, the noised multiplication is logically:

```
A'_e = A_e + E_A,e
W'_e = W_e + E_W,e
C'_e = A'_e * W'_e
```

where the noise factors are derived from the grouped commitments and `sigma`.

The implementation SHOULD share noising and peeling work across experts whenever the same activation rows or shared weight-side noise factors are reused. In particular, because the expert weights are stacked, the weight-side left noise factor may be shared across all experts:

```
W         := stacked expert matrix of shape d x (n_E * h)
E_BL      := shared weight-side left noise factor of shape d x R
T_EBL     := T * E_BL
T_EBL,e   := GatherRows(T_EBL, route[e])
```

`T_EBL` is computed once over the global activation matrix and then gathered for each expert. This avoids recomputing the same activation-by-noise product for each expert-local multiplication.

The exact distributions of low-rank factors, domain separators, and noised matrix encodings MUST match version-1 security requirements unless explicitly overridden by the version-2 reference implementation.

### Verifier Algorithm

Given a block with a version-2 certificate, a verifier performs the following checks.

#### 1. Parse Certificate

The verifier checks:

```
certificate.version == 2
mu.mode == GROUPED_GEMM
```

and parses the version-2 public witness data.

#### 2. Check Seed Derivation

The verifier recomputes `H_T_grouped`, `s_W`, and `s_T` from the public commitments, routing offsets, and `job_key`.

#### 3. Authenticate Routing Elements

For the opened expert `e` and opened expert-local row positions, the verifier checks Merkle authentication paths against `H_R`, proving that the exposed token indices are the committed routing entries at those positions.

If the opened expert-local row positions are:

```
j_0, j_1, ..., j_{r-1}
```

then the verifier obtains:

```
route[e][j_0], route[e][j_1], ..., route[e][j_{r-1}]
```

and checks that the exposed sequence is monotonic in tile order.

#### 4. Authenticate Activation Rows

For each exposed token index `q`, the verifier checks an authentication path against `H_T`, proving that the opened activation row equals `T[q, :]`.

This is the main difference from version 1. In version 1, the opened row belongs directly to the committed left matrix at the same row position. In version 2, the opened row of `A_e` belongs to the global activation matrix at row `route[e][j]`.

#### 5. Authenticate Expert Weight Slice

The verifier checks authentication paths against `H_W`, proving that the opened weight features belong to the contiguous slice `W_e` of the stacked expert-weight matrix.

The verifier also checks that `expert_index = e` maps to the claimed slice according to `mu.weight_slice_layout`.

#### 6. Check the Opened Noised Tile Relation

Using the authenticated activation rows, authenticated weight columns or feature strips, authenticated routing entries, and public data required by the SNARK statement, the verifier checks the version-2 opened tile relation.

Logically, the relation is:

```
A_e[j, :] = T[route[e][j], :]
W_e       = Slice(W, e)
A'_e      = A_e + E_A,e
W'_e      = W_e + E_W,e
M         = TileHashTrace(A'_e, W'_e, opened_tile_position, opened_depth_index)
```

#### 7. Check Proof-of-Work Target

The verifier checks:

```
opened_hash_value <= Target(mu.difficulty_bits, work_tile)
```

where `opened_hash_value` is the version-2 hash of the opened accumulator state, and `work_tile` is computed from the exposed tile dimensions and certified trace depth.

#### 8. Verify the zkSNARK

The verifier verifies the version-2 zkSNARK over the public data committed by `pouw_meta`.

A block is valid only if all checks pass.

### zkSNARK Statement

Version 2 extends the version-1 SNARK statement from a dense matrix opening to a routing-aware grouped-GEMM opening. The proof system and recursive compression strategy are inherited from version 1.

The version-2 statement is:

> There exist private activation rows, expert-weight strips, routing authentication data, and low-rank-noise witness values such that: (1) the routing entries are consistent with `H_R`; (2) the opened expert-local activation rows equal the rows of `T` selected by those routing entries and are consistent with `H_T`; (3) the opened expert-weight strips belong to the contiguous expert slice committed by `H_W`; (4) the prescribed noised grouped-GEMM tile computation yields accumulator state `M`; and (5) the public hash of `M` satisfies the version-2 target for the effective useful work in the opened tile.

The following values are public:

```
mu
H_T
H_W
H_R
expert_index
opened_tile_position
opened_depth_index
opened routing entries for the jackpot tile
opened_hash_value
```

Activation values, weight values, non-opened routing entries, and non-opened trace values remain private except insofar as they are implied by the public data and proof validity.

### Block and Consensus Effects

This PIP changes consensus validation by adding certificate version `0x02`. It does not change:

- transaction validity;
- the UTXO model;
- block subsidy calculation;
- difficulty adjustment;
- block identity calculation, except that `pouw_meta` commits to version-2 public witness data;
- script semantics.

A version-2 block MUST be rejected if:

- the certificate is not parseable as version 2;
- the grouped-GEMM mode is not recognized;
- the routing commitment is malformed;
- any exposed routing element fails authentication;
- any exposed activation row fails authentication against `H_T`;
- any exposed expert-weight strip fails authentication against `H_W`;
- the opened tile hash fails the target check;
- the zkSNARK fails verification;
- effective-work normalization uses anything other than the opened tile's certified useful multiply-add count.

### Why expose jackpot routing entries?

The opened tile location is public, as in version 1. In version 2, the verifier also needs the routing entries that map opened expert-local rows to global activation rows. Exposing only the jackpot tile's routing entries is sufficient to verify the opened relation while keeping the rest of the routing table unopened.

### Why normalize by opened effective work?

Proof-of-work fairness requires the chance of winning to be proportional to performed useful work. In grouped GEMM, full declared shapes can be misleading because active token-expert assignments vary by expert and batch. Normalizing by the opened tile's useful multiply-add count prevents a miner from claiming probability mass from inactive or unauthenticated work.

## Backwards Compatibility

This PIP is not backwards compatible with nodes that only understand Pearl PoUW certificate version `0x01`. Blocks using certificate version `0x02` require upgraded consensus validation. The upgrade is therefore a hard fork.

Wallets, addresses, transaction relay, mempool policy unrelated to PoUW certificates, and script validation are unaffected.

Miners that do not run MoE workloads may continue to mine using version-1 certificates until activation rules say otherwise.

## Privacy Considerations

The version-2 certificate reveals the expert index, opened tile position, opened feature positions, and routing entries needed to map jackpot expert-local rows to global token rows. It does not reveal non-opened activation rows, non-opened expert-weight values, or non-opened routing entries.

The SNARK statement should hide activation and weight values for the opened computation, except for public commitments and tile metadata. Implementations SHOULD avoid including raw activation or weight values in public witness data.

## Appendix: Non-normative Miner Notes

The following notes describe one workable miner implementation. They are not normative; alternative miner implementations that produce a valid version-2 certificate are conformant.

### Miner Algorithm

A version-2 miner performs the following steps.

#### 1. Preprocess Expert Weights

The miner stores all expert weights in one contiguous matrix:

```
W = [W_0 || W_1 || ... || W_{n_E-1}]
```

where each `W_e` has shape `d x h`. The miner commits to `W` as `H_W`. This commitment may be reused across token batches when the weights do not change, subject to chain-state-dependent seed derivation.

#### 2. Commit to Activations

Given a token batch, the miner commits once to the global activation matrix `T` in token-major order, producing `H_T`.

An activation routed to several experts is committed as one row of `T`, rather than being serialized and hashed separately in each expert-local matrix.

#### 3. Commit to Routing

The miner computes or receives the MoE routing table and commits to it as `H_R`. The protocol verifies consistency with the committed routing table; it does not verify how the routing table was produced.

The routing commitment binds the ordered token-index list for each expert:

```
route[e] = [token_index_0, token_index_1, ...]
A_e[j, :] = T[route[e][j], :]
```

#### 4. Derive Seeds

The miner derives `s_W` and `s_T` as specified in the Seed Derivation section. All randomness used for noising, tile hashing, and opening MUST be domain-separated from version 1.

#### 5. Noise and Execute Grouped GEMM

For each expert `e`, the miner forms `A'_e` and `W'_e` and executes:

```
C'_e = A'_e * W'_e
```

The computation uses a tiled matrix-multiplication trace compatible with the version-1 inner hash. For each output tile, the miner maintains the prescribed accumulator digest and tests the proof-of-work predicate.

Miners SHOULD use GPU-native grouped-GEMM kernels rather than independent GEMM launches. The certificate is intended to follow the execution shape of real MoE workloads.

#### 6. Peel Noise

The miner recovers the useful output by subtracting the low-rank correction terms. Version 2 is designed so that duplicated activation-side peeling work is computed once globally and then gathered into expert-local order.

Compared with running version 1 independently for every expert, version 2 saves:

- repeated commitment hashing of duplicated activation rows;
- repeated noising of expert-local activation matrices;
- repeated multiplication of the same activation rows by shared weight-side noise factors;
- repeated verifier reasoning about standalone `A_e` commitments.

Remaining costs include routing gathers and scatters, peeling terms that scale with token-expert assignments, memory bandwidth for small expert-local tiles, and scheduling overhead when experts are imbalanced.

#### 7. Produce a Winning-Tile Certificate

When a tile satisfies the difficulty predicate, the miner constructs a version-2 certificate proving the opened tile relation. The certificate binds the block to one grouped-PoUW instance through `pouw_meta`.

### Opened Tile Public Data

For an accepted tile belonging to expert `e`, the public data committed by `pouw_meta` includes:

```
certificate_version = 2
mu
H_T
H_W
H_R
expert_index = e
opened_tile_position
opened_depth_index
opened_token_indices
opened_weight_feature_indices
opened_hash_value
```

The opened tile position identifies the expert-local row interval and the weight-feature interval of the jackpot tile. The corresponding token indices from `route[e]` are exposed for the opened rows, allowing the verifier to connect expert-local rows of `A_e` to rows of `T`.

The certificate MUST NOT claim work credit from full declared matrix shapes. Difficulty accounting is based only on the effective useful multiply-add operations in the opened tile.

### Difficulty Predicate

Let an opened full tile have effective dimensions:

```
rows  := number of opened expert-local activation rows
cols  := number of opened expert-weight output features
depth := common dimension certified by the opened trace
```

The effective useful work of the opened tile is:

```
work_tile := rows * cols * depth
```

The target for the opened tile MUST be normalized by `work_tile`, or by the equivalent implementation-specific count of useful multiply-add operations represented by the opened trace.

The verifier MUST NOT scale the target by the number of experts, the full activation shape, or the full stacked-weight shape. Only the exposed tile dimensions and certified trace depth contribute to the winning probability.
