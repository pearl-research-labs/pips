## Abstract

Pearl Proof-of-Useful-Work (PoUW) certificates (versions 1 and 2, see [PIP-2](./pip-0002.md) [1]) prove *integer* noised matrix multiplications: operands are committed as INT8 values with one bit of headroom (INT7). This PIP specifies a new protocol in which the operands are floating-point matrices. Henceforth, the previous and new protocols are referred to as the *INT Protocol* and the *FP Protocol* respectively.

Certificate version 3 becomes mandatory at the activation height: version 1 and 2 certificates are rejected from this height onward. We stress that version 3 certificates are not valid under version 1 or 2 validation rules. Activation is therefore a consensus hard fork: upgraded nodes MUST parse and verify version 3 certificates according to this specification, while non-upgraded nodes will reject blocks using this certificate version.

## Motivation

The FP protocol aims to facilitate useful work.

1. **Floating Point Support.** The overwhelming majority of AI models are natively floating-point. The FP protocol is designed to work directly with floating-point matrices, whereas the previous protocol used integer-valued matrices.
2. **Low Overhead.** The FP protocol enables an almost perfect “Two-For-One,” incurring significantly smaller overhead compared to the INT protocol.

### Caveats

We highlight several caveats and differences from the existing INT protocol:

1. **Lossiness.** Unlike the INT protocol, the output of the FP protocol does not match the expected output in a bit-exact fashion. Despite these errors at the matrix-multiplication level, empirically, the models we tested do not exhibit noticeable differences in accuracy.
2. **Quantization.** The INT protocol replaced the single atomic operation of multiplying two matrices, whereas the new FP protocol replaces a slightly more involved operation: quantization to FP8 (E4M3) followed by matrix multiplication. We expand on the relevance of this operation in the context of AI inference below.
3. **Hardware and Implementation Dependence.** Different architectures and different implementations yield different outputs (bitwise). Therefore, the miner is required to declare the hardware it uses in advance, and both the miner and the verifier follow a specific computation on the declared hardware.

### Quantization

Modern inference alternates between low-precision and high-precision data types:

1. Matrix Multiplication: Input matrices `A, B` are in a low-precision data type. The multiplication accumulates into a high-precision accumulator (e.g., `FP8 @ FP8 -> FP32`).
2. Quantization: Output `C` is converted back to the lower-precision representation.

In essence, this pattern appears in virtually every modern inference pipeline. We will not delve into the technical motivation behind it.

### High-Level Overview

The FP protocol exploits the quantization operator in two ways:

1. **Security.** Quantization is a non-linear map whose behavior has no exploitable structure - computing a product of quantized matrices offers no shortcut even when the quantized matrices are low-rank. This is the computational unpredictability of the hardness assumption in the Security Assumption section.
2. **Accuracy.** Models tolerate quantization noise - in many cases by design [4-6]. The FP protocol only increases the existing quantization noise by a small factor.

We describe a simplified version of the FP protocol below.

```
# Q is a quantization operator, and @ denotes matrix multiplication.
# NA, NB are low-rank noise matrices (in the full protocol NA = E1 @ F1, NB = E2 @ F2).
A' = Q(A + NA)                                    # m x k, quantized
B' = Q(B + NB)                                    # n x k, quantized
C''  = (A' - NA) @ (B' - NB).T                    # m x n, useful output
```

The output does not equal the expected true matrix multiplication `Q(A) @ Q(B).T`, but rather is very close to it (as in general, `Q(A) ~ A` but not equal). As the noise matrices are chosen to be of constant low rank (`r = 32`, independent of the other parameters), the computation of `C''` is not much slower than that of `Q(A) @ Q(B)`.

## Specification

### Certificate Version

This PIP assigns Pearl PoUW certificate version 3 to the FP protocol.

```
certificate := version || bytes
version     := 3
```

As in prior versions, certificate bytes are not part of the block identifier. The certificate carries the selected ancestor header (see Depth), the public parameters of both operands, the two tile bases, and Merkle openings of the selected rows of `A` and `B`. Roots, seeds, noise, and the product tile are recomputed by the verifier and not carried.

### The FP Protocol

The protocol consists of a *prover* (miner) and a *verifier*. An honest prover takes operands (matrices) `A, B` and performs the following computation:

```
0. INPUT: A in BF16(m x k), B in BF16(n x k)
1. PRE-QUANTIZATION: A, B are encoded in the FP10 commit format (see Commitment)
2. COMMITMENT:
  # H is a hash function
  - COMMIT B to H(B), and A to H(A)
3. NOISE GENERATION:
  - GENERATE E1 in FP8(m x r) FROM H(A) and H(B)
  - GENERATE F1 in FP8(r x k) FROM H(B)
  - GENERATE E2 in FP8(n x r) FROM H(B)
  - GENERATE F2 in FP8(r x k) FROM H(B)
4. QUANTIZE:
  # @ denotes matrix multiplication of the input dtypes using FP32 accumulator
  # Q is a quantization operator (row-wise) defined below to FP8
  - A' = Q(A + E1 @ F1)                             # m x k, quantized
  - B' = Q(B + E2 @ F2)                             # n x k, quantized
5. MATRIX MULTIPLICATION & LOTTERY:
  - C' = A' @ B'.T
  - CHECK FOR WINNING TICKETS ON TILES OF C'
6. PEEL:
  # || denotes concatenation of matrices horizontally
  - A'' = [E1                     ||  A' @ F2.T ]   # m x 2r
  - B'' = [(E2 @ F2 - B') @ F1.T  ||  -E2       ]   # n x 2r
  - C'' = A'' @ B''.T
7. OUTPUT C' + C''
```

With the added peeling correction term, the reader may verify that `C' + C''` is mathematically equivalent to the useful output `C` from the High-Level Overview section (here `C''` denotes only the correction), showing it approximates the true matrix multiplication up to the rounding error due to the quantization.

The listing omits scales: `Q` multiplies each row by a per-row factor before the FP8 cast, so a matching descale must be applied when forming the useful output. Lottery tickets use the scaled `C'`.

The verifier architecture remains unchanged, adapted to verify the above computation (ZK, see [7]). Note that the verifier is required to be able to reproduce floating-point computation on the specific committed hardware **in a bit-exact fashion**. Hardware is therefore whitelisted, and the exact arithmetic is specified in [7]. As a consequence the miner is also restricted to a specific computation (see Reference Implementation).

### Commitment

As in prior versions, `H(A)` and `H(B)` are commitment hashes binding the operand bytes, their shapes, chain state etc., and support openings of individual rows. For more details on how the commitment is implemented, see the Pearl whitepaper [7].

Operands are committed in the **FP10** format: an `INT8` value per entry plus one `BF16` scale per block of 8 consecutive entries in a row (10 bits per entry). Each operand is a Merkle tree over its rows (values and scales as two trees under one aggregate root). The row norms used by quantization are computed from this representation, so they are exact and reproducible.

The public parameters - dimensions, `r`, the quantization scheme, the device (Blackwell), the hash identifiers, and the tile patterns - are bound into the noise seeds together with the commitment roots and the chain state. The miner therefore fixes them before learning its noise.

### Depth: allowing noise from previous state

We allow the miner to use a previous state of the chain for the commitment of `B`: the commitment is keyed by any header within a window of depth `D` (e.g., `D = 3`) ending at the proposed block, while `A` is always bound to the proposed header. In practice, this means that the miner can use the same noise for `B` for multiple blocks, allowing the operand `B` to stay fixed. The selected header is carried in the certificate.

### Noise Generation

All noise factors are deterministic functions of the commitments: `E1` is derived from `H(A), H(B)`, and `E2, F1, F2` from `H(B)` alone. Draws MUST come from the canonical sampler specified in [7], fed with a keyed BLAKE3 [3] stream. Every implementation MUST reproduce the draws in a bit-exact fashion.

The distribution is real-valued and symmetric, normalized per row so that the noise is small yet not negligible relative to the values subjected to it: rows of `E1, E2` are drawn with an expected squared norm determined by a noise scale, and columns of `F1, F2` with expected unit squared norm.

### Quantization

Row-wise quantization: each row `i` is multiplied by a single floating-point scale `α[i]` and rounded to the nearest representable FP8 (E4M3) value. Equivalently, `A'[i] = Q(A)[i] = FP8(α[i] · A[i])`. The scale is a deterministic function of row `i` such that the scaled row fits the FP8 dynamic range (maximum `448.0` [2]). The exact procedure is specified in [7]. Note that tickets are computed from the scaled `A'` and `B'`, and the peeling therefore requires scaling/descaling the relevant terms accordingly.

### Block Resolution

The output `A' @ B'.T` is partitioned into tiles committed in advance by the miner. Each tile is compressed by a committed extractor into a short message whose keyed BLAKE3 [3] hash is the lottery ticket. A ticket wins if it falls below the consensus target scaled by the tile’s arithmetic work, as in prior versions. Unlike the INT protocol, we do not have a *transcript* - the winning tickets are computed only on the single matrix product `C'` (no intermediate computations are needed). Winning tickets are subject to an additional verifier-side check (the Jackpot Policy below): statistical tests on the opened tile that reject degenerate or predictable noised computations.

### Jackpot Policy

As the FP protocol has been outlined until this point, it can be exploited via the following attack based on floating-point arithmetic.

**Floating-Point Attack**
In order to simplify the presentation, we focus on a single dot product of two vectors, e.g., the first rows of `A, B`. Recall that `A, B` are for the attacker to choose, so take them to be the one-hot vectors

```
v = (1, 0, 0, ...)
```

Denote `v'` the quantized noised version of `v` - note that each operand is noised via fresh randomness (hence we get different vectors). However, both vectors will have a very specific structure (with high probability)

```
v' = (448.0, X1, X2, ...)
```

with the remaining entries `Xi` equal to the scaled-down noise, hence much smaller than `448`. The `448.0` is the maximum possible FP8 value (we could possibly also get smaller values close to it, e.g., `416.0`) and comes from the quantization step (regardless of the noise). The problem is that the dot product of two such vectors is dominated by `448.0²`, and the accumulator truncates every summand below its grid at that magnitude. The miner knows in advance which noise-carrying summands round away and can skip them. In the extreme, the result is **bit-exact predictable** regardless of the noise. This breaks the security of the protocol, and the input can be perturbed to obtain different tickets with very little additional computation.

The solution to this problem is to enforce that operands satisfy statistical properties that ensure that the noise affects the ticket in a significant way. The verifier runs several checks specified in [7].

## Rationale

### Hardware Dependence

Hardware dependence is a necessary evil in floating-point protocols. The future seems to be abundant with various floating-point data types that provide infinitely many different flavors of accuracy/speedup tradeoff, e.g., the already ubiquitous MXFP8, NVFP4. While the FP protocol is not agnostic to the data type, this proposal is a first step toward a protocol supporting further useful workloads.

### Why determinism instead of tolerance checks?

Any tolerance in verification becomes vulnerable to grinding attacks. E.g., the miner can perturb the output and get many tickets without doing additional computation.

### Pre-Quantization

We allow pre-quantizing the matrices in a more memory-efficient format, thus reducing the overhead (specifically, of the commitment). FP10 spends 10 bits per entry instead of 16 for BF16, while the block scales keep the decoded values within BF16 rounding of the originals. The protocol does not mandate the encoding procedure, but a recommended construction appears in [7].

### Lottery

The tickets are the tiles of the intermediate `C' = A' @ B'.T` rather than those of the final output `C' + C''`. This gives the miner more flexibility in the peeling process.

### Committed Noise

We highlight that the noise matrices `F1, E2, F2` depend solely on `B`, and only `E1` depends on `A`. This might look odd at first because `E1, F1` are the noise factors of `A` and `E2, F2` are that of `B`. The motivation is amortization over `B''`: in the peeling step (see "The FP Protocol" section), `B''`, which is the second peeling part, depends on all three noise factors `F1, E2, F2`, and `B'`. In the context of useful work, `B` stands for the weight matrix and is fixed throughout a block. Therefore, this design choice enables the computation of `B''` per block (rather than per matrix multiplication).

### Depth

The idea is very similar to the "Committed Noise" section above - allowing better amortization over `B` thus speeding up useful mining. Specifically, each time we need to re-noise `B`, this forces reading the original weight matrix from the storage, which incurs some overhead. The depth relaxation allows the miner not only to use the same noise for `B` for a longer period of time, but also gives more flexibility in timing when swapping out `B` for a new one.

## Backwards Compatibility

This PIP is not backwards compatible with nodes that only understand Pearl PoUW certificate versions 1 and 2. Blocks using certificate version 3 require upgraded consensus validation.

## Security Assumption

For simplicity, we focus on the case where the adversary provides the zero matrices. In this case, the protocol reduces to computing

```
Q(E1 @ F1) @ Q(E2 @ F2).T
```

The underlying security assumption is that computing the matrix multiplication of quantized low-rank matrices is as hard as for general (unstructured) matrices of the same dimensions.
