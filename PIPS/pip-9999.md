## Abstract

The FP protocol of [PIP-3](./pip-0003.md) [1] requires the verifier to replay the FP8 matrix multiplication of the committed `Device` bit-for-bit, and whitelists only Hopper (`0`) and Blackwell (`1`). NVIDIA Ada Lovelace GPUs (compute capability 8.9: GeForce RTX 40-series, RTX 6000 Ada, L4, L40, L40S) have native FP8 tensor cores but match neither profile. Their FP8 MMA keeps Hopper's 13-bit accumulation window but collapses every 16 products instead of every 32. Because version 1–3 certificates are rejected from the PIP-3 activation height, every Ada GPU would stop mining at that fork.

This PIP adds `Device = 2` (Ada). Its matrix multiplication is the Appendix C.2 [2] group step with `W = 13` and a group size of 16 products. The groups are arranged in 128-product windows, and each window's local accumulator is promoted into an FP32 total with one round-to-nearest-even addition. It also specifies the jackpot-policy magnitudes and noise constants for the new device. Silicon measurements on an RTX 4070 Ti SUPER (AD103) match this specification on every one of 1,662,976 output cells that use this structure. This PIP asks that `Device = 2` be accepted from the same activation height as PIP-3, so that no additional hard fork is needed.

## Motivation

1. **Ada miners stop at the FP fork.** INT-protocol verification (certificate versions 1–3) is device-independent integer arithmetic, and Ada GPUs mine it today with third-party miners. The FP protocol accepts only devices whose arithmetic the verifier replays. The reference miner refuses compute capability 8.9 ("no committed mining Device for sm89"), and the verifier fails closed on any device byte other than `0` or `1`. Without an Ada device, this whole class of hardware leaves the network at the PIP-3 activation height.
2. **Ada is a large installed base of FP8 inference hardware.** Compute capability 8.9 supports `mma.sync` with E4M3 operands and FP32 accumulation natively. Mainstream inference stacks (vLLM, TensorRT-LLM) serve FP8 models on it. Data-center Ada parts (L4, L40S) are widely deployed for inference, which is the useful work PIP-3 targets.
3. **The arithmetic is simple and deterministic.** Ada's FP8 MMA is an instance of the PIP-3 Appendix C.2 model with different architecture-dependent parameters (see Specification). The verifier changes are a new parameter set, not a new arithmetic model.

For throughput context: GeForce Ada runs FP8 with FP32 accumulation at about half its INT8 tensor rate (RTX 4090: 330.3 dense FP8/FP32-accumulate TFLOPS versus 660.6 dense INT8 TOPS, per NVIDIA's specification). Ada miners would therefore produce fewer FP-protocol tickets per card than they do INT-protocol tickets today. This PIP does not change the difficulty target or ticket weighting. Tickets from every device are weighted by the same `|I_A| · |I_B| · k`.

## Specification

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in RFC 2119.

This PIP extends the FP protocol of PIP-3 and the arithmetic of the Pearl Floating Point Scheme Specification [2] (cited below as "the whitepaper"). Everything not stated here is unchanged.

### Device enumeration

The consensus-allowed `Device` list becomes:

```
Device := 0  // Hopper    (PIP-3)
        | 1  // Blackwell (PIP-3)
        | 2  // Ada       (this PIP)
```

The device byte is committed in `pB` and bound into the noise seeds exactly as for the existing devices. A verifier implementing this PIP MUST accept `Device = 2` and MUST continue to reject every other unknown value. The device names an arithmetic profile, not a hardware attestation. Any miner MAY commit `Device = 2`, and its tiles verify only if they are bit-exact under `MatMul_ADA`.

### `MatMul_ADA`

Wherever the FP protocol invokes `MatMul_Device` with `Device = 2`, the verifier MUST compute `MatMul_ADA` as specified here. This includes the lottery product `A' · B'^T` and the rank-`r` noise products `E · F^T` used by quantization. Operands are E4M3FN as in whitepaper Appendix C.1. For `U ∈ FP8^(a×k)` and `V ∈ FP8^(b×k)` with `k` a positive multiple of 32, each output cell `(i, j)` is:

```
MatMul_ADA(U, V)[i, j]:
  total ← +0                                    // FP32
  for s in 0, 128, 256, ... while s < k:        // windows, ascending
    e ← min(s + 128, k)                         // the last window may be partial
    c ← +0                                      // window-local accumulator
    for t in s, s + 16, s + 32, ... while t < e:   // groups, ascending
      c ← Group13(c, U[i, t .. t+15], V[j, t .. t+15])
    total ← RNE_FP32(total + c)                 // reject if not finite
    if total = 0: total ← +0
  return total
```

`Group13(c, a, b)` is the group step of whitepaper Appendix C.2 with internal precision `W = 13` and 16 products per group:

```
input:          a, b ∈ FP8^16, c ∈ FP32
products:       p_u ← a_u · b_u  for u = 0, ..., 15                (exact)
exponent shift: η ← max( ε(c), max_u { ε(a_u) + ε(b_u) } )         (over nonzero terms)
summation:      S ← Trunc(c, 2^(η−13)) + Σ_u Trunc(p_u, 2^(η−13))  (exact)
zero:           if S = 0: return +0
rounding:       return Trunc(S, 2^(⌊log2 |S|⌋ − 13))
```

`ε`, `Trunc`, and the treatment of unnormalized products and subnormal operands are as defined in whitepaper Appendix C.2. If all terms are zero the group returns `+0`. Because `W = 13 ≤ 23`, the result is exactly representable in FP32, and no output rounding step applies.

Equivalently, each 32-product MMA atom of the PIP-3 Hopper model is replaced by two consecutive 16-product groups. The first group consumes the carry `c` and products `0..15`. The second consumes the first group's result `S1` and products `16..31`. All other structure is the same as the Hopper replay of the Pearl reference implementation [3]: 128-product windows starting from `+0`, one FP32 RNE promotion per window, and a partial last window when `128 ∤ k`.

### Device constants

`Device = 2` uses the following constants. Each derived quantity is computed by the same formula as for the existing devices.

```
fp8_window_bits      W         = 13
lg2_delta                      = 0      // delta = 1
liveness_code_shift            = (3 + lg2_delta) · 128 = 384
sigma_encoding_offset          = 14 + lg2_delta        = 14
```

Quantization (whitepaper Appendix C.4) is otherwise device-independent. It MUST use `delta = 1` and `MatMul_ADA` for the noise product.

### Jackpot policy magnitudes

The jackpot policy of PIP-3 (whitepaper Section 5.1 and Appendix C.5) is unchanged except for the replay magnitudes, which are taken from `MatMul_ADA`. For cell `(i, j)`:

- `M_ij` is the largest magnitude over every exact product `|U[i,u] · V[j,u]|`, and over the exact, unrounded value `|total + c|` after **every** `Group13` step. Here `total` is the promoted total before the current window.
- `Z_ij,s` is the largest magnitude over the exact products of window `s` and over `c` after every `Group13` step in window `s`.

Both maxima include the first-group partial `S1` of every atom. Hopper never forms this intermediate, and it can exceed every product and every atom result (see Test Vectors). The unpredictable-summands check then uses the Hopper form of the grid, with `W = 13`. Summand `u` is judged against the `Z` of the window that contains it:

```
q      = max( e(Z_ij,s) − 13, e(M_ij) − 18 )      // zero magnitudes omitted
E_GRID = q + 157                                  // 0 only when M and Z are both zero
```

The constants `τ_idle, ε_idle, σ_min, τ_tame, ε_tame, ε_pred`, the skip budget, and the integer `lambda` rule are those of PIP-3 for every device.

### Activation

`Device = 2` SHOULD be accepted from the PIP-3 activation height (`Fp8ForkHeight`), so that it activates together with the FP protocol's certificate version (version 4 in the reference implementation and in the pending PIP-3 revision). If PIP-3 activates without it, `Device = 2` MUST NOT be accepted before a separately announced activation height.

## Rationale

### A new device rather than emulation

Ada cannot commit `Device = 0` or `1` and have its tiles verify. Hopper's rule aligns and truncates 32 products against one shared exponent, and no sequence of 16-product collapses reproduces that in general. Zero-padding half of each instruction still yields "carry + 16 products" per collapse. The only way to produce Hopper or Blackwell bits on Ada is CUDA-core emulation of the data-dependent alignment. For scale, a contributor's bit-exact software path for the B200 profile on Apple M5 ran about 35–100× slower than that chip's native INT8 rate ([pips#14](https://github.com/pearl-research-labs/pips/issues/14)). Emulation is not a viable mining path.

### Why 16-product groups

That is what the hardware does. On sm_89, `mma.sync.aligned.m16n8k32.row.col.f32.e4m3.e4m3.f32` is the only FP8 MMA shape, and it compiles to native `QMMA.16832.F32.E4M3.E4M3`. On every tested input it behaves as two `Group13` steps per instruction, with the carry entering the first group and products `k = 0..15` collapsing before `16..31`. The width matches the 13-mantissa-bit FP8 accumulator reported for the RTX 4090 in prior work [6]. The grouping is the difference from Hopper.

### Why windowed promotion

Ada silicon matches the `Group13` rule both as a continuous chain (whitepaper C.2 applied across all of `k`) and in the 128-product windowed structure. This PIP specifies the windowed structure for three reasons:

1. **Accuracy.** A continuous chain of 13-bit collapses loses precision as `k` grows, up to `k = 2^16`. Promoting every 128 products into FP32 bounds that loss, which is the reason the Hopper replay promotes.
2. **Policy admissibility.** With a continuous chain, `Z = M` grows with the full dot product, so more honest summands fall below a 13-bit grid. Window-local `Z` keeps honest tiles inside the unpredictable-summands budget, as it does for Hopper.
3. **Cost and reuse.** Promotion costs one FP32 addition per 128 products per output cell. The window structure, its policy magnitudes, and its circuit layout already exist for Hopper in the reference implementation [3]. Ada changes only the group size inside the window.

This PIP does not depend on Hopper remaining whitelisted. The window structure is fully specified above, so it stands on its own if PIP-3 activates with Blackwell only.

### Why `lg2_delta = 0`

The unpredictability grid `ulp_Device(x) = 2^(⌊log2 |x|⌋ − W)` depends only on `W`, and Ada's `W` equals Hopper's. Using Hopper's full-strength noise keeps the noise-to-grid ratio that PIP-3 chose for a 13-bit window. Ada's extra intermediate `S1` is accounted for in `Z` and `M` instead (see Security Considerations). The noise strength is the parameter the PIP-3 authors are best placed to revisit, and a different value would change only the constants above.

### Why value `2` and activation with PIP-3

`2` is the next unused discriminant. The current verifier rejects it, so adding it is a pure relaxation and cannot change the validity of any proof that commits `0` or `1`. PIP-3 has not activated, and the reference implementation sets `Fp8ForkHeight` only for regtest and simnet. Including Ada in the same activation therefore costs nothing in compatibility. Adding it later would require a second hard fork, and every Ada miner would have been offline in between.

### Evidence

The harness ran the warp-level instruction above on an RTX 4070 Ti SUPER (AD103, Linux driver 580.178.04). Its outputs were compared bit-for-bit against a C++ port of the verifier arithmetic that passes the reference implementation's own `B200_FP8_VECTORS` and Hopper replay tests. The run covered 35 suites and 3,227,648 output cells:

- single atoms with zero, random, and 13-bit FP32 carries
- uniform, narrow-exponent, subnormal-heavy, and Gaussian E4M3 operands
- exact half-atom cancellation, and ±0 carries
- continuous chains and 128-product promoted windows at `k` = 128, 256, 1024, 1120 (partial window), and 4096

| Model | Suites bit-exact on Ada |
|---|---|
| PIP-3 Hopper replay | 8 / 35 |
| PIP-3 Blackwell | 3 / 35 |
| `Group13` with 16-product groups | 35 / 35 |

The matching suites are those where no truncation occurs (integer sums, narrow exponents with zero carry, subnormal-only inputs), so they cannot tell the profiles apart. On Gaussian operands at `k = 4096`, a Hopper-structured Ada kernel agrees with the Hopper replay on 27.7 % of cells, so its tiles effectively never verify as `Device = 0`. An RTX 5090 and an RTX 5070 Ti, both compute capability 12.0, ran the same suites as controls. They match Blackwell on all cells and the 16-group model on only 3 / 35 suites.

The Rust reference in `assets/pip-9999/ada_replay.rs` was checked separately against the same silicon outputs. It matches all 1,662,976 cells of the 17 suites whose structure is `MatMul_ADA` itself: 13 promoted-window suites and 4 single-atom suites from `+0`. The Hopper replay matches 1,210,756 of those cells (72.8 %). A later rerun of all 35 suites on the same card was bit-identical to the original outputs (see the discussion thread).

## Backwards Compatibility

This PIP changes consensus only for proofs that commit `Device = 2`, which every current verifier rejects. Proofs that commit `Device = 0` or `1` verify exactly as before: the device byte is bound into the noise seeds, so a proof's device cannot be reinterpreted.

If this PIP activates together with PIP-3, it adds no incompatibility beyond PIP-3's own hard fork. If it activates later, accepting `Device = 2` is itself a hard fork: nodes without it reject blocks whose certificate commits `Device = 2`.

Mining software needs no change to keep working on Hopper and Blackwell. Ada mining requires an FP8 kernel that reproduces `MatMul_ADA`, together with the miner-side device mapping (see Reference Implementation).

## Security Considerations

**Replay remains the ground truth.** The verifier recomputes the opened tile with `MatMul_ADA` and accepts only a bit-exact match. Chain safety therefore never depends on whether any particular GPU conforms to this specification. A non-conforming device produces tiles that fail verification, which costs its operator but not the network. Only the AD103 die has been measured. Other compute capability 8.9 dies (AD102, AD104, AD106, AD107) and data-center parts (L4, L40, L40S, RTX 6000 Ada) share the Ada SM and are expected to conform, but they have not been measured.

**No cross-device ticket reuse.** The device byte is part of `pB` and therefore of every noise seed. A miner cannot compute one tile and test it under several devices' arithmetic: a different device yields different noise and a different tile.

**Policy soundness with 16-product groups.** The second group of each atom is aligned to `max(ε(S1), ε(p_16..31))`. When `|S1|` exceeds every product, as it does when a group's products add coherently, products `16..31` are truncated against a coarser grid than the products alone would set. The policy accounts for this by including every group result in `Z` and `M` (Specification). This makes Ada's unpredictable-summands check at least as strict as one computed from products and atom results alone. Without `S1` in `Z`, the check could under-count skippable summands.

**Precision shortcuts.** Ada truncates each product once, against its group's anchor, and truncates the first-group result again in the second group. This is the same class of truncation the whitepaper's precision-shortcut analysis and jackpot policy address for Hopper, with no wider window. The noise strength (`lg2_delta = 0`) is chosen to match Hopper's. Review by the PIP-3 authors is requested.

**Other hardware may commit `Device = 2`.** Under the PIP-3 Hopper model, a Hopper GPU can reproduce `MatMul_ADA` by zero-padding each 32-product instruction to 16 live products. Zero products do not affect the alignment exponent. This costs it twice the instructions of its native profile, so it gains nothing over committing `Device = 0`. The same holds for any emulation on hardware without a native 16-group, 13-bit FP8 MMA.

**Non-finite values.** As for every device, a non-finite intermediate result, including an FP32 overflow at promotion, causes verification failure.

## Privacy Considerations

This PIP has no privacy implications.

## Reference Implementation

- [`assets/pip-9999/ada_replay.rs`](../assets/pip-9999/ada_replay.rs) is a standalone Rust implementation of `MatMul_ADA` and of its policy magnitudes `Z`/`M`. It reuses the arithmetic of the Pearl reference implementation [3] (`GFloat`, `multiply_fp8_to_gfloat`, `windowed_group_sum`, and the Hopper window loop) and changes only the group size. Its tests check the silicon vectors, check that the Hopper replay differs from them, and reproduce the reference implementation's own Hopper promotion and policy tests through the same code path. Build it with `rustc --edition 2021 --test ada_replay.rs` (no dependencies).
- The required changes to the Pearl verifier (`zk-pow`) are:
  - **Plaintext verification:** add `Device::ADA = 2` to the enum, `ALL`, and `TryFrom<u8>`; add the constants above; dispatch `matmul_fp8` to an Ada replay (the Hopper replay with a 16-product group); and add an Ada arm to the jackpot policy census that uses per-window grids as for Hopper.
  - **Zero-knowledge verification:** add a matmul STARK for Ada, a variant of the Hopper matmul STARK that steps one 16-product group per row, plus the matching cross-table lookups, consistency checks, and unpredictability constraints. It must expose the first-group partial to `Z` and `M`.
  - **Verifier-work admission:** the reference branch's admission score (`verifier_work_units`) takes per-device table geometry. Ada's entry follows from its matmul STARK and is to be determined with it.
- Miner software (non-consensus) needs to map compute capability 8.9 to `Device = 2` in the reference miner's device table, and needs an sm_89 FP8 kernel built on `mma.sync` with one FP32 promotion per 128 products.

The standalone replay is complete. The in-crate integration and the matmul STARK have not been started. The author intends to implement them against the reference branch once the parameters above are agreed.

## Test Vectors

All values are FP32 bit patterns. Operand bytes are E4M3FN codes, `a` is `m × k` and `b` is `n × k`, both row-major, as in the reference implementation's `B200_FP8_VECTORS`. Inline operands are hex strings, one byte per two digits, in `k` order.

**Single atom from `+0`** (`m = n = 1`, `k = 32`), measured on silicon:

```
a = 3234b828bbc59a38a62a3f1a3bb9a6bc36a9b6b4223a3b88aaba3b3c2b363bab
b = b0382a291c3da4a7b133bcb93c360eab3d39afb5ae123db5289737211d2ab9b5

MatMul_ADA  = 0xBFC2B000   (-1.5209961)   Ada silicon
MatMul_H100 = 0xBFC2A800   (-1.5207520)
```

**Promoted windows**, measured on silicon. These four vectors are in [`assets/pip-9999/ada_fp8_vectors.rs`](../assets/pip-9999/ada_fp8_vectors.rs), each with its Hopper result for contrast, and each differs from Hopper in at least one cell:

| Vector | Shape `m × n × k` | Covers |
|---|---|---|
| 1 | 2 × 2 × 128 | one full window, Gaussian operands |
| 2 | 2 × 2 × 128 | one full window, uniform E4M3 codes |
| 3 | 2 × 2 × 256 | two windows, one FP32 promotion |
| 4 | 1 × 1 × 1120 | eight full windows and a partial 96-product window |

In vector 1, cell `(0, 1)` gives `0xC408E800` (−547.625) on Ada, against `0xC408F000` (−547.75) on Hopper.

**Policy magnitudes** (derived from this specification). Take `k = 32`, `a = [0x38] × 16 ‖ [0xB8] × 16` (sixteen +1.0 then sixteen −1.0), and `b = [0x38] × 32`. Both devices return `+0`. On Ada, `S1 = 16`, so `e(Z) = [4]` and `e(M) = 4`. On Hopper the single collapse never forms 16, so `e(Z) = [0]` and `e(M) = 0`.

**Noise atom** (derived from this specification). The fixed seed-address lines in the reference implementation's `device_quantization_pins_noise_alpha_beta_and_code` test (`e = be3adfea…dd65`, `f = c6526860…54e3`, `k = r = 32`) do not separate the devices. `MatMul_ADA` gives `0x45382000`, the same as Hopper. With `delta = 1` that test's quantization outputs for `Device = 2` therefore equal Hopper's: `alpha = 17002`, `beta = 15269`, code `105`.
