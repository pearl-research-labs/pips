## Abstract

The FP protocol of [PIP-3](./pip-0003.md) [1] requires the verifier to replay the FP8 matrix multiplication of the committed `Device` bit-for-bit. It whitelists only Hopper (`0`) and Blackwell (`1`). AMD RDNA4 GPUs (gfx1200 and gfx1201: Radeon RX 9060, RX 9070 and Radeon AI PRO R9700) have native FP8 matrix instructions that run at their full INT8 rate, but their arithmetic matches neither profile. RDNA4 sums products in 8-product groups, each pre-summed in two quads of 4. It keeps 24 fractional bits, floors each aligned term, and rounds each group to FP32 nearest-even. Because version 1–3 certificates are rejected from the PIP-3 activation height, every RDNA4 GPU would stop mining at that fork.

This PIP adds an RDNA4 `Device`. Its matrix multiplication, `MatMul_RDNA4`, is a continuous chain of 8-product group steps with no window promotion, structurally like the Blackwell profile. The PIP specifies the group step, the device constants and the jackpot-policy magnitudes. Silicon measurements on an RX 9070 XT (gfx1201) and an RX 9060 XT (gfx1200) match this specification on all 2,998,272 measured output cells, and the two dies are bit-identical to each other. This PIP asks that the device be accepted from the same activation height as PIP-3, so that no additional hard fork is needed.

## Motivation

1. **RDNA4 miners stop at the FP fork.** INT-protocol verification (certificate versions 1–3) is device-independent integer arithmetic, and RDNA4 GPUs mine it today with third-party miners. The FP protocol accepts only devices whose arithmetic the verifier replays. The verifier fails closed on any device byte other than `0` or `1`, and the reference miner supports NVIDIA GPUs only. Without an RDNA4 device, this whole class of hardware leaves the network at the PIP-3 activation height.
2. **FP8 runs at the full matrix rate on RDNA4.** `v_wmma_f32_16x16x16_fp8_fp8` (E4M3 operands, FP32 accumulation) issues at the same rate as the INT8 `v_wmma_i32_16x16x16_iu8`. At the same board power cap we measured FP8 at 99.7 % (RX 9070 XT, 356 TOPS) and 99.5 % (RX 9060 XT, 193 TOPS) of INT8 throughput. Moving from the INT to the FP protocol therefore costs RDNA4 miners no raw matrix throughput. ROCm inference stacks serve FP8 models on this hardware, which is the useful work PIP-3 targets.
3. **The arithmetic is simple and deterministic.** It is a fixed-point group sum of the same family as the Appendix C.2 [2] model, with different architecture-dependent parameters. The verifier changes are a new group step inside the existing Blackwell-style continuous chain.

This PIP does not change the difficulty target or ticket weighting. Tickets from every device are weighted by the same `|I_A| · |I_B| · k`.

## Specification

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in RFC 2119.

This PIP extends the FP protocol of PIP-3 and the arithmetic of the Pearl Floating Point Scheme Specification [2] (cited below as "the whitepaper"). Everything not stated here is unchanged.

### Device enumeration

The consensus-allowed `Device` list gains one value, `RDNA4`:

```
Device := 0  // Hopper    (PIP-3)
        | 1  // Blackwell (PIP-3)
        | 3  // RDNA4     (this PIP)
```

The discriminant `2` is left to the pending Ada proposal ([pips#16](https://github.com/pearl-research-labs/pips/pull/16)). If that proposal is not adopted, editors MAY assign `RDNA4` the next unused value instead. Nothing in this PIP depends on the number. The device byte is committed in `pB` and bound into the noise seeds exactly as for the existing devices. A verifier implementing this PIP MUST accept the `RDNA4` value and MUST continue to reject every other unknown value. The device names an arithmetic profile, not a hardware attestation. Any miner MAY commit `RDNA4`, and its tiles verify only if they are bit-exact under `MatMul_RDNA4`.

### `MatMul_RDNA4`

Wherever the FP protocol invokes `MatMul_Device` with `Device = RDNA4`, the verifier MUST compute `MatMul_RDNA4` as specified here. This includes the lottery product `A' · B'^T` and the rank-`r` noise products `E · F^T` used by quantization. Operands are E4M3FN as in whitepaper Appendix C.1. For `U ∈ FP8^(a×k)` and `V ∈ FP8^(b×k)` with `k` a positive multiple of 8, and an optional FP32 carry-in `C`, each output cell `(i, j)` is:

```
MatMul_RDNA4(U, V, C)[i, j]:
  c ← C[i, j] if C is present, else +0          // FP32
  for t in 0, 8, 16, ... while t < k:           // groups, ascending
    c ← G8(c, U[i, t .. t+7], V[j, t .. t+7])
  return c
```

There is no window promotion: the group results chain through the whole of `k`, as in the Blackwell profile.

**Products.** For E4M3 codes `x, y`, write `e(x)` for the exponent field, read as `1` when it is `0` (subnormal), and `m(x)` for the significand: `8 + mantissa` if the field is nonzero, else `mantissa`. The product `p = x · y` is exact. Its stored exponent is `ε(p) = e(x) + e(y) − 14`, and `|p| = m(x) · m(y) · 2^(ε(p) − 6)`, with `m(x) · m(y) < 2^8`. This is the unnormalized product of the reference implementation's `multiply_fp8_to_gfloat` [3]. Products with `m(x) · m(y) = 0` are *zero products* and take no part in any maximum below.

**Group step** `G8(c, a_0..a_7, b_0..b_7)`, with `p_u = a_u · b_u` and `Floor(v, 2^g)` the largest multiple of `2^g` not above `v` (rounding toward −∞):

```
if every p_u is a zero product:
    return c, with -0 replaced by +0
quads:     Q0 = (p_0 .. p_3), Q1 = (p_4 .. p_7)
           for each quad Q with a nonzero product:
             η_Q ← max { ε(p) : p ∈ Q nonzero }
             S_Q ← Σ_{p ∈ Q} Floor(p, 2^(η_Q − 24))               (exact)
anchor:    η ← max( max_u ε(p_u),  E(c) − 2 )                      (E(c) term only if c ≠ 0)
summation: S ← Σ_Q Floor(S_Q, 2^(η − 24))  +  K                    (exact)
           K ← Floor(c, 2^(η − 24)) if c ≠ 0 and E(c) ≥ η − 24, else 0
zero:      if S = 0: return +0
rounding:  return RNE_FP32(S)                                       (reject if not finite)
```

`E(c)` is the unbiased exponent of the FP32 carry, `−126` for FP32 subnormals. `RNE_FP32` rounds the exact value to the nearest FP32 value, ties to even, including FP32 subnormal results.

Notes for implementers:

- A carry with `E(c) < η − 24` lies wholly below the group grid. It is discarded, not floored to `−2^(η−24)`.
- The quad anchors satisfy `η_Q ≤ η`, so the quad step never coarsens the group grid.
- All intermediate sums fit in a signed 64-bit integer in units of `2^(η − 24)`.

### Device constants

`RDNA4` uses the following constants. Each derived quantity is computed by the same formula as for the existing devices.

```
fp8_window_bits      W         = 24
lg2_delta                      = -1     // delta = 1/2, as for Blackwell
liveness_code_shift            = (3 + lg2_delta) · 128 = 256
sigma_encoding_offset          = 14 + lg2_delta        = 13
```

Quantization (whitepaper Appendix C.4) is otherwise device-independent. It MUST use `delta = 1/2` and `MatMul_RDNA4` for the noise product.

### Jackpot policy magnitudes

The jackpot policy of PIP-3 (whitepaper Section 5.1 and Appendix C.5) uses the Blackwell form for `RDNA4`: a single window over all of `k`, with `Z_ij = M_ij`. `M_ij` is the largest magnitude over every exact product `|U[i,u] · V[j,u]|` and over the FP32 accumulator `|c|` after **every** `G8` step (`k / 8` partials per cell). The grid is then the Blackwell one:

```
q      = max( e(M_ij) − 24, e(M_ij) − 18 ) = e(M_ij) − 18     // zero magnitudes omitted
E_GRID = q + 157                                              // 0 only when M is zero
```

Because `W = 24 ≥ 18`, the grid exponent is the same function of `M` as for Blackwell. Only the partials that feed `M` change. The constants `τ_idle, ε_idle, σ_min, τ_tame, ε_tame, ε_pred`, the skip budget, and the integer `lambda` rule are those of PIP-3 for every device.

### Activation

`RDNA4` SHOULD be accepted from the PIP-3 activation height (`Fp8ForkHeight`), so that it activates together with the FP protocol's certificate version (version 4 in the reference implementation and in the pending PIP-3 revision). If PIP-3 activates without it, `RDNA4` MUST NOT be accepted before a separately announced activation height.

## Rationale

### A new device rather than emulation

RDNA4 cannot commit `Device = 0` or `1` and have its tiles verify. The Blackwell profile aligns 32 products and the carry against one anchor, truncates terms toward zero, and rounds group results toward zero. RDNA4 collapses every 8 products, pre-sums quads against their own anchors, floors terms, and rounds to nearest-even. No zero-padding or reordering of the 16-deep instruction changes any of these. A bit-exact Blackwell emulation would need integer matrix instructions over exponent bands, plus data-dependent per-term truncation for every 32-product group of every cell. For scale, a contributor's bit-exact software path for the Blackwell profile on Apple M5 ran about 35–100× slower than that chip's native INT8 rate ([pips#14](https://github.com/pearl-research-labs/pips/issues/14)). Emulation is not a viable mining path. The native path runs at the full rate.

### Why this group step

That is what the hardware does. `v_wmma_f32_16x16x16_fp8_fp8` (wave32 and wave64) behaves as two `G8` steps per instruction, with the carry entering the first. The structure was isolated with targeted probes, each confirmed on both dies:

- **Two groups.** A `+B, −B, x` cancellation probe over every slot triple shows the two chained 8-product groups. A tiny `x` survives only when both `B` terms sit in an earlier group.
- **Quads.** A probe with two sub-grid terms shows the quads. The terms keep their exact sum only when the large products sit in the other quad.
- **Floor at 24 bits.** Grid probes (`2^e` plus a tiny negative product) give a floor at `2^(ε − 24)`.
- **RNE output.** Tie-maker probes give nearest-even output rounding.
- **Carry anchor and drop rule.** A sweep of negative carries gives the carry anchor `E(c) − 2` and the rule that drops a carry wholly below the grid.

The model was then checked against random and structured data (see Evidence). The carry anchor reflects the operand formats: products carry two integer bits above `ε`, the FP32 carry one.

### Why a continuous chain

A 24-bit window does not need promotion. This is the Blackwell argument: the precision lost per group is far below that of a 13-bit window, and the silicon instruction already chains the FP32 accumulator. A continuous chain needs no extra FP32 additions in the miner. It also reuses the Blackwell policy shape: one window and `Z = M`.

### Why these constants

The coarsest grid relative to the largest magnitude is `2^(e − 24)` for products and `2^(E(c) − 26)` for the carry, so `W = 24`. That is one bit coarser than Blackwell's 25, and far finer than Hopper's 13. Blackwell's `lg2_delta = −1` was chosen for a window of this class, so this PIP proposes the same. As the policy section shows, the unpredictable-summands grid of a `W ≥ 18` device depends only on `M`. The noise strength is the parameter the PIP-3 authors are best placed to revisit, and a different value would change only the constants above.

### Why the value and activation with PIP-3

`3` avoids the value requested by the pending Ada PIP. The current verifier rejects it, so adding it is a pure relaxation and cannot change the validity of any proof that commits `0` or `1`. PIP-3 has not activated, and including RDNA4 in the same activation costs nothing in compatibility. Adding it later would require a second hard fork, and every RDNA4 miner would be offline in between.

### Evidence

The harness runs the instruction above, chained over `k`, on an RX 9070 XT (gfx1201, Navi 48) and an RX 9060 XT (gfx1200, Navi 44) under ROCm 7 (HIP 7.16). It compares outputs bit-for-bit against a C++ port of the verifier arithmetic. The port passes all of the reference implementation's `B200_FP8_VECTORS`, its Hopper replay unit tests, and the four Ada silicon vectors of pips#16. Each card ran 93 suites with 1,499,136 output cells:

- **Single instructions** (`k = 16`) with these carries: zero, Gaussian, 13-bit, ±0, FP32-subnormal, very large, very small, and arbitrary finite FP32 bit patterns.
- **Operand distributions:** uniform, narrow-exponent, subnormal-heavy, subnormal-only and two Gaussian E4M3 distributions.
- **Structured inputs:** exact half-instruction, quad and pairwise cancellation; all-zero and all-negative-zero products; sparse operands.
- **Continuous chains** at `k` = 32, 128, 256, 1024, 1120, 4096 and 16384, with and without carry-in.

| Model | Suites bit-exact (per card) |
| --- | --- |
| PIP-3 Hopper replay | 3 / 27 (suites where it applies: no carry, `32 \| k`) |
| PIP-3 Blackwell | 34 / 93 |
| Ada (pips#16) | 3 / 27 |
| `MatMul_RDNA4` | 93 / 93 |

The suites the other profiles match are those where no truncation occurs. On Gaussian operands at `k = 4096`, the Blackwell profile agrees with RDNA4 silicon on 34.5 % of cells, so RDNA4 tiles effectively never verify as `Device = 1`. The two cards' outputs are byte-identical on all 93 suites, and the wave64 form of the instruction matches `MatMul_RDNA4` on all 65,536 cells tested.

## Backwards Compatibility

This PIP changes consensus only for proofs that commit `RDNA4`, which every current verifier rejects. Proofs that commit `Device = 0` or `1` verify exactly as before: the device byte is bound into the noise seeds, so a proof's device cannot be reinterpreted.

If this PIP activates together with PIP-3, it adds no incompatibility beyond PIP-3's own hard fork. If it activates later, accepting `RDNA4` is itself a hard fork: nodes without it reject blocks whose certificate commits `RDNA4`.

Mining software needs no change to keep working on Hopper and Blackwell. RDNA4 mining requires an FP8 kernel that reproduces `MatMul_RDNA4`. With the native instruction this is the natural layout: in wave32, lane `l` holds `k0 + 8·⌊l/16⌋ + 0..7`, so each lane loads 8 contiguous bytes per operand.

## Security Considerations

**Replay remains the ground truth.** The verifier recomputes the opened tile with `MatMul_RDNA4` and accepts only a bit-exact match. Chain safety therefore never depends on whether any particular GPU conforms to this specification. A non-conforming device produces tiles that fail verification, which costs its operator but not the network. Only the Navi 48 and Navi 44 dies have been measured. Other gfx12 parts share the RDNA4 matrix datapath and are expected to conform, but they have not been measured.

**No cross-device ticket reuse.** The device byte is part of `pB` and therefore of every noise seed. A miner cannot compute one tile and test it under several devices' arithmetic: a different device yields different noise and a different tile.

**Policy soundness.** Every intermediate that sets a grid is accounted for:

- The group anchor is set by products and the carry, and both enter `M`.
- The quad pre-sum anchors at or below the group anchor, so it never drops a term that the group grid would keep.
- Group results are FP32 values that enter `M` as partials.

This makes the unpredictable-summands check at least as strict as for Blackwell on the same magnitudes.

**Precision shortcuts.** RDNA4 floors each product once against its quad anchor and each quad sum once against the group anchor. This is the same class of rounding the whitepaper's precision-shortcut analysis and jackpot policy address for Blackwell. The window is one bit narrower and the groups are four times shorter. Review of the noise strength by the PIP-3 authors is requested.

**Other hardware may commit `RDNA4`.** Any device can commit it by reproducing `MatMul_RDNA4`, in software or otherwise. Hardware without a native RDNA4-style FP8 group step has no reason to prefer it over its own profile.

**Non-finite values.** As for every device, a non-finite intermediate result, including FP32 overflow in a group step, causes verification failure.

## Privacy Considerations

This PIP has no privacy implications.

## Reference Implementation

- [`assets/pip-9999/rdna4_replay.rs`](../assets/pip-9999/rdna4_replay.rs) is a standalone Rust implementation of `MatMul_RDNA4`. It reuses the arithmetic of the Pearl reference implementation [3]: `GFloat` and `multiply_fp8_to_gfloat` for the products, plus `windowed_group_sum` and the Blackwell loop for contrast. Its tests check the silicon vectors in [`assets/pip-9999/rdna4_fp8_vectors.rs`](../assets/pip-9999/rdna4_fp8_vectors.rs), check that the Blackwell model differs from them, and pin each structural rule above (quad anchoring, the two chained groups, floor, carry anchor and drop, signed zeros) with cells re-measured on silicon. Build it with `rustc --edition 2021 --test rdna4_replay.rs` (no dependencies).
- The required changes to the Pearl verifier (`zk-pow`) are:
  - **Plaintext verification:** add the `RDNA4` variant to `Device`, `ALL`, and `TryFrom<u8>`; add the constants above; dispatch `matmul_fp8` and `matmul_fp8_partials` to an RDNA4 replay; and add an `RDNA4` arm to the jackpot policy census that mirrors Blackwell with `k / 8` partials.
  - **Zero-knowledge verification:** add a matmul STARK for RDNA4, a variant of the Blackwell matmul STARK that steps one 8-product group (two quads) per row, plus the matching cross-table lookups, consistency checks, and unpredictability constraints. It has four times as many group rows per `k` as Blackwell.
  - **Verifier-work admission:** the reference branch's admission score (`verifier_work_units`) takes per-device table geometry. The RDNA4 entry follows from its matmul STARK and is to be determined with it.
- Miner software (non-consensus) needs to map gfx1200/gfx1201 to `RDNA4` and needs a gfx12 FP8 kernel built on `v_wmma_f32_16x16x16_fp8_fp8`.

The standalone replay is complete. The in-crate integration and the matmul STARK have not been started. The authors intend to implement them against the reference branch once the parameters above are agreed.

## Test Vectors

All values are FP32 bit patterns. Operand bytes are E4M3FN codes, `a` is `m × k` and `b` is `n × k`, both row-major, as in the reference implementation's `B200_FP8_VECTORS`. Inline operands are hex strings, one row per line, in `k` order.

**Single instruction with carry-in** (`m = n = 2`, `k = 16`), measured on silicon:

```
a = dac4624d2edb51e1dbcfd5c828cd55df
    5d54d9d4b44dde63e0484f5dbbd44ecd
b = 5a59574650d559c85856c958cb5b40d8
    54b3ce5ce2ca5ac0d4cc4c41d6e0dfca
c = 381BE595 49C23120 37C84EF9 C76C1B97

MatMul_RDNA4 = 4425D800 49C23668 C40BAC00 C76B6717   RDNA4 silicon
MatMul_B200  = 4425D800 49C23668 C40BABFF C76B6717
```

**Chains**, measured on silicon. These five vectors are in [`assets/pip-9999/rdna4_fp8_vectors.rs`](../assets/pip-9999/rdna4_fp8_vectors.rs), each with its Blackwell result for contrast, and each differs from Blackwell in at least one cell:

| Vector | Shape `m × n × k` | Covers |
| --- | --- | --- |
| 1 | 2 × 2 × 16 | one instruction, Gaussian operands, random carry (above) |
| 2 | 2 × 2 × 16 | one instruction, uniform codes, arbitrary-bit carry |
| 3 | 2 × 2 × 128 | chain from `+0`, Gaussian operands |
| 4 | 2 × 2 × 256 | chain, uniform codes, arbitrary-bit carry |
| 5 | 1 × 1 × 1120 | chain with `128 ∤ k` |

**Structural cells** (`k = 16`, measured on both dies; the Rust tests pin each of these). Here `x@u` means product `x` at position `u`:

- `16384@0, −2^-18@1` gives `16384 − 2^-10`: floor against the quad anchor. Blackwell gives `16384`.
- `16384@0, −14336@1, −2^-11@5, 3·2^-11@6` gives `2048 + 2^-10`: separate quad anchors. With the two small terms at positions 2 and 3 instead, the result is `2048`.
- `16384@0, −16384@1, 2^-12@12` gives `2^-12`: two chained groups. With the ±16384 pair at 8 and 9 and `2^-12` at 2, the result is `+0`.
- Carry `2^24` with `1.5@0` gives `16777218`: RNE output. Blackwell's round-toward-zero gives `16777216`.
- `36@0, 2^-18@4` with carry `−2^-20` gives `36 + 2^-18`: the carry is dropped. With carry `−2^-19`, the result is `36`.
- Carry `−0` with only zero products gives `+0`. A nonzero carry with only zero products passes through unchanged.

**Noise atom.** On the fixed seed-address lines of the reference implementation's `device_quantization_pins_noise_alpha_beta_and_code` test (`e = be3adfea…dd65`, `f = c6526860…54e3`, `k = r = 32`), `MatMul_RDNA4` gives `0x45382200`, measured on both dies. That is the Blackwell value. With `delta = 1/2`, that test's quantization outputs for `RDNA4` therefore equal Blackwell's: `alpha = 17082`, `beta = 15236`, code `109`.
